## FINDING DP-001: Python Scripts in `docs/qc/`

**Severity: MEDIUM**
**Files affected: 11 .py files**
**Action required: Owner approval (code move)**

### Files

| File | Size (approx) | Purpose |
|---|---|---|
| `docs/qc/b7p01_capability_registry_validation.py` | ~200 lines | Validates capability registry data |
| `docs/qc/b7p02_entitlement_resolution_validation.py` | ~200 lines | Validates entitlement resolution logic |
| `docs/qc/b7p03_config_resolution_validation.py` | ~200 lines | Validates config resolution hierarchy |
| `docs/qc/b7p04_commerce_flow_validation.py` | ~200 lines | Validates commerce workflow |
| `docs/qc/b7p05_payment_adapter_validation.py` | ~200 lines | Validates payment adapter integration |
| `docs/qc/b7p06_communication_workflow_validation.py` | ~200 lines | Validates communication workflow |
| `docs/qc/b7p07_delivery_system_validation.py` | ~200 lines | Validates delivery system |
| `docs/qc/b7p08_end_to_end_system_validation.py` | ~200 lines | End-to-end system validation |
| `docs/qc/load_test_readiness_check.py` | ~100 lines | Load test readiness check |
| `docs/qc/p18_end_to_end_validation.py` | ~100 lines | End-to-end validation |
| `docs/qc/performance_smoke_tests.py` | ~100 lines | Performance smoke tests |

### What These Are

These are standalone Python validation scripts that:
- Import from Python stdlib (`pathlib`, `json`, `dataclasses`)
- Read repository files to validate consistency
- Output results as JSON reports (to `docs/qc/*.json`)
- Were created during Phase 0 (U0–U11) development auditing

### Why This Is a Problem

1. `docs/` is a documentation directory. Executable source code in `docs/` violates the principle that docs/ contains only `.md` documentation files.
2. A developer looking for validation tooling would search `validation/`, `scripts/`, or `tests/` — not `docs/`.
3. A documentation consumer reading `docs/` may accidentally execute a script.
4. `docs/` may be published or exported as documentation; scripts should not be part of that export.

### Recommended Resolution

**Move scripts to `validation/` directory:**

```
docs/qc/b7p01_*.py → validation/b7p01_*.py
...
docs/qc/performance_smoke_tests.py → validation/performance_smoke_tests.py
```

`validation/` already exists at root with 4 .py files — this is its stated purpose.

**Leave in docs/qc/:**
- All `.md` QC reports (36 files) — these ARE documentation
- All `.json` output reports (9 files) — these are generated by the scripts

**If scripts reference relative paths (`../..` etc.), those paths must be updated after move.**

**Owner approval required:** Yes — this is a code move, not a documentation update.

## FINDING DP-002: JSON Capability and Schema Files in `docs/architecture/`

**Severity: LOW**
**Files affected: 8 .json files**
**Action required: Owner determination**

### Files

`docs/architecture/capabilities/`:
```
B0P05_business_capabilities.json    — Business capability definitions
B0P06_communication_capabilities.json — Communication capability definitions
B0P07_delivery_capabilities.json    — Delivery capability definitions
B0P08_intelligence_capabilities.json — Intelligence capability definitions
```

`docs/architecture/schemas/`:
```
capability_registry.schema.json     — JSON Schema for capability registry
capability_registry.example.json    — Example capability registry document
segment_configuration.schema.json   — JSON Schema for segment config
segment_configuration.example.json  — Example segment config document
```

### Analysis

**Capability JSON files (4):** These are machine-readable capability definitions with the legacy `B0P0X` batch naming. They may be:
- Input data for the capability-registry service (belongs in `backend/services/capability-registry/`)
- Reference documentation for developers (acceptable in `docs/architecture/`)
- Imported by `docs/qc/*.py` scripts for validation (explains co-location)

**Schema JSON files (4):** These are JSON Schema validation files. They may be:
- Used at runtime by the capability-registry service (belongs in `backend/services/capability-registry/`)
- Used by the `docs/qc/*.py` validation scripts (explains co-location)
- Documentation artifacts showing the data contract (acceptable in `docs/architecture/schemas/`)

### Current Risk

Low — these files are not documentation but they are co-located with the docs that reference them. Moving them could break `docs/qc/*.py` scripts that may import or load them using relative paths.

### Recommended Resolution

**OPTION A (Preferred):** Leave in place and document.
Add `docs/architecture/capabilities/README.md` and `docs/architecture/schemas/README.md` noting these are reference artifacts for the capability-registry service and QC scripts, retained in docs/ for co-location with their documentation.

**OPTION B (Ideal long-term):** Move to capability-registry service.
`docs/architecture/capabilities/*.json` → `backend/services/capability-registry/data/`
`docs/architecture/schemas/*.json` → `backend/services/capability-registry/schemas/`
Update `docs/qc/*.py` script paths accordingly. Requires code change — owner approval.

**Immediate action:** None. Document the current state.

## FINDING DP-003: JSON Artifacts in docs/governance/ and docs/specs/

**Severity: LOW**
**Files affected: 2 .json files**
**Action required: None (informational)**

### Files

- `docs/governance/spec_index.json` — A generated index file. Likely created by a script that indexed the specs/ directory. Purpose: provides a machine-readable catalogue of spec files.

- `docs/specs/B0P04_core_capabilities.json` — A JSON capability spec file with the B0P04 legacy naming. This is the earlier batch document that preceded the capability-inventory.md structure.

### Analysis

**spec_index.json:** Appears to be a generated catalogue. If no script actively reads it, it is an outdated artifact. If a script reads it as an index of available specs, it should be kept current.

**B0P04_core_capabilities.json:** Legacy capability data. The `B0P04` naming convention is from the original BATCH document naming scheme (pre-governance). This file is a peer to the B0P05–B0P08 files in `docs/architecture/capabilities/` but is in `docs/specs/`. Its content is superseded by docs/specs/capability-inventory.md and docs/specs/capability-domain-map.md.

### Action

No immediate action. Both files are low-risk placements. Document as known non-documentation artifacts.

## FINDING DP-004: Empty Numbered Directories in `docs/`

**Severity: LOW**
**Directories: docs/01_backend/, 02_frontend/, 03_ops/, 04_testing/, 05_deployment/**
**Action required: None (correct structure)**

### Analysis

These 5 directories are intentionally empty. They are placeholders for future authority documentation:
- `01_backend/` → Backend authority docs (planned: Backend Authority Capture phase)
- `02_frontend/` → Frontend authority docs (planned: Phase 2 Frontend)
- `03_ops/` → Operations authority docs
- `04_testing/` → Test strategy docs
- `05_deployment/` → Deployment strategy docs

**Finding:** The placeholder structure is correct per the governance plan. The only consumer confusion risk is a developer or AI session scanning `docs/` and wondering if content is missing.

**Recommendation:** Low priority. Could add `docs/01_backend/PLACEHOLDER.md` explaining each empty directory's purpose and planned phase. Not required.
